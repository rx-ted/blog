# Next.js + Cloudflare Workers 运行与部署规范

## 1. 目标

项目使用 Next.js + OpenNext 部署到 Cloudflare Workers。

运行环境只保留两套：

1. **Local**：本地开发和本地预览，使用本地模拟资源。
2. **Production**：生产环境，使用 Cloudflare 远程资源。

不额外引入 Staging、Testing 等环境，避免配置和维护复杂化。

## 2. 技术栈

| 类别            | 技术                                     |
| --------------- | ---------------------------------------- |
| Web Framework   | Next.js 16                               |
| UI              | React 19                                 |
| Language        | TypeScript                               |
| Runtime         | Cloudflare Workers                       |
| Adapter         | @opennextjs/cloudflare                   |
| CLI             | Wrangler 4                               |
| Database        | Cloudflare D1                            |
| Object Storage  | Cloudflare R2                            |
| Cache           | Cloudflare KV                            |
| AI              | Cloudflare Workers AI                    |
| Package Manager | pnpm                                     |
| Code Quality    | ESLint / Biome（按项目实际迁移情况启用） |

继续使用 OpenNext，不引入 vinext 或 MCP。

## 3. 运行环境

### 3.1 环境划分

| 命令                 | 运行方式                  | 资源来源   | 用途             |
| -------------------- | ------------------------- | ---------- | ---------------- |
| `pnpm dev`           | Next.js Dev Server        | Local      | 日常开发         |
| `pnpm preview:local` | Cloudflare Preview Worker | Local      | 本地生产构建验证 |
| `pnpm preview:prod`  | Cloudflare Preview Worker | Production | 使用生产资源验证 |
| `pnpm deploy`        | Cloudflare Workers        | Production | 正式部署         |

注意：

- `preview:local` 和 `preview:prod` 都是在本地启动 Preview Worker。
- `preview:local` 使用本地模拟资源，适合离线和日常验证；首次或需要重建本地数据时，先执行 `pnpm cf:local:init`。
- `preview:prod` 只是连接生产资源，不会部署代码。
- `deploy` 才会将 Worker 发布到 Cloudflare。
- 生产资源应谨慎操作，Preview 阶段尽量使用只读操作，避免修改真实数据。

### 3.2 运行流程

```text
                    Development
                         |
                    pnpm dev
                         |
                   Local Resources


                     Preview
                         |
                 pnpm preview:local
                         |
                   Local Resources
                         |
                  OpenNext Build


                 Production Preview
                         |
                 pnpm preview:prod
                         |
                 Production Resources
                         |
                  OpenNext Build


                    Production
                         |
                   pnpm deploy
                         |
                 Production Resources
                         |
                  Cloudflare Workers
```

## 4. Cloudflare 资源

### 4.1 资源清单

| 服务            | Binding                 | 用途                   |
| --------------- | ----------------------- | ---------------------- |
| D1              | `DB`                    | 关系型数据库           |
| R2              | `IMAGES`                | 图片及文件存储         |
| KV              | `CACHE`                 | 缓存                   |
| Workers AI      | `WORKERS_AI`            | AI 能力                |
| Assets          | `ASSETS`                | OpenNext 静态资源      |
| Service Binding | `WORKER_SELF_REFERENCE` | Worker 自引用          |
| Queues          | `BACKGROUND_QUEUE`      | 后台任务队列，按需启用 |
| Vectorize       | `VECTOR_INDEX`          | 向量检索，按需启用     |

Cloudflare Workers 还提供以下运行时能力：

- Cache API：`caches.default`
- `ctx.waitUntil()`：延迟执行后台任务
- Durable Objects：有状态协调和持久化对象

注意：项目代码中存在某项服务的接口或功能，不代表 Wrangler 已经完成对应 Binding、资源创建和部署配置。只有实际配置并创建的资源才可以使用。

### 4.2 资源配置原则

Local 和 Production 使用相同的 Binding 名称，但绑定不同的资源。

| Binding      | Local              | Production      |
| ------------ | ------------------ | --------------- |
| `DB`         | 本地 D1            | 生产 D1         |
| `IMAGES`     | 本地 R2 模拟       | 生产 R2         |
| `CACHE`      | 本地 KV 模拟       | 生产 KV         |
| `WORKERS_AI` | 本地模拟或按需远程 | 生产 Workers AI |

这样业务代码不需要根据环境判断资源名称，只需要通过 Binding 获取资源。

## 5. Wrangler 配置

### 5.1 配置文件

推荐保留：

```text
wrangler.jsonc
wrangler.local.jsonc
wrangler.prod.jsonc
```

- `wrangler.jsonc`：示例/模板配置，可提交到 GitHub，不写入真实资源 ID、密钥或个人环境信息。
- `wrangler.local.jsonc`：本地真实配置，用于本地开发/预览。
- `wrangler.prod.jsonc`：生产真实配置，用于生产资源预览/部署。
- `wrangler.local.jsonc` 与 `wrangler.prod.jsonc` 内容通常保持一致，主要用于区分环境和绑定目标；实际差异由资源绑定模式和运行命令决定。
- 不在代码中硬编码生产数据库 ID、KV Namespace ID 等信息。

实际使用哪个配置文件由 `scripts/cf-config.sh` 统一决定。一般规则：本地命令优先使用 `wrangler.local.jsonc`，生产命令优先使用 `wrangler.prod.jsonc`；缺少对应配置时可回退到 `wrangler.jsonc` 模板，但模板不应包含真实生产资源。

### 5.2 配置示例

以下仅展示 `wrangler.jsonc` 模板的配置结构，具体 ID、资源名称和 OpenNext 生成配置以项目实际情况为准。真实配置放在 `wrangler.local.jsonc` / `wrangler.prod.jsonc`。

```jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "qiaomu-blog",
  "main": "worker.ts",
  "compatibility_date": "2026-11-25",
  "compatibility_flags": ["nodejs_compat"],

  "assets": {
    "directory": ".open-next/assets",
    "binding": "ASSETS"
  },

  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "qiaomu-blog-db",
      "database_id": "YOUR_DATABASE_ID"
    }
  ],

  "r2_buckets": [
    {
      "binding": "IMAGES",
      "bucket_name": "qiaomu-blog-images"
    }
  ],

  "kv_namespaces": [
    {
      "binding": "CACHE",
      "id": "YOUR_KV_NAMESPACE_ID"
    }
  ],

  "services": [
    {
      "binding": "WORKER_SELF_REFERENCE",
      "service": "qiaomu-blog"
    }
  ]
}
```

说明：

1. `compatibility_date` 应根据项目实际依赖和 Cloudflare 兼容性要求确定，不要机械使用示例日期。
2. `database_id`、KV ID 等应填写真实资源 ID，但不要写入提交到 GitHub 的 `wrangler.jsonc` 示例；真实值放在 `wrangler.local.jsonc` / `wrangler.prod.jsonc`。
3. `wrangler.local.jsonc` 与 `wrangler.prod.jsonc` 内容通常一致；本地命令使用本地模拟/本地状态，生产命令连接远程生产资源。
4. 生产配置不要提交 API Token、密码等敏感信息。
5. 项目使用自定义 `worker.ts` 包装 OpenNext handler 时，`main` 应指向 `worker.ts`；不要机械照搬 `.open-next/worker.js` 示例。
6. OpenNext 可能需要额外的 Durable Objects、迁移或 Service Binding 配置，应以当前版本的 OpenNext 配置要求为准。

## 6. Next.js 与 OpenNext

### 6.1 OpenNext 配置

项目使用：

```text
open-next.config.ts
worker.ts
wrangler.jsonc
wrangler.local.jsonc
wrangler.prod.jsonc
```

OpenNext 负责将 Next.js 应用转换为 Cloudflare Workers 可运行的产物。

构建产物：

```text
.open-next/
├── worker.js
├── assets/
└── ...
```

### 6.2 获取 Cloudflare Context

在需要访问 Cloudflare Binding 的服务端代码中，使用 OpenNext 提供的 Cloudflare Context。

```ts
import { getCloudflareContext } from '@opennextjs/cloudflare'

const { env } = await getCloudflareContext()

const db = env.DB
```

开发环境需要初始化 OpenNext 的本地开发支持。

项目当前通过 `next.config.ts` 中的 `initOpenNextCloudflareForDev()` 处理开发环境初始化。

不要在普通业务模块中自行创建 Cloudflare 资源实例。

### 6.3 环境变量与 Binding

区分两种配置：

**Binding：**

- D1
- R2
- KV
- Workers AI
- Service Binding

**环境变量 / Secrets：**

- 第三方 API Key
- OAuth Client Secret
- 邮件服务凭据
- 其他敏感配置

Cloudflare Binding 优先于通过环境变量传递资源连接信息。

## 7. package.json 命令

统一提供以下主要入口：

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "opennextjs-cloudflare build",

    "preview:local": "pnpm cf:preview:local",
    "preview:prod": "pnpm cf:preview:remote",

    "deploy": "pnpm cf:deploy",

    "cf:local:init": "bash scripts/cf-local-init.sh",
    "cf:types": "wrangler types"
  }
}
```

这里的 `cf:preview:local`、`cf:preview:remote`、`cf:deploy`、`cf:local:init` 对应项目脚本或其统一封装。Cloudflare 相关脚本统一使用 `cf:` 前缀。

具体职责：

| 命令            | 职责                                                          |
| --------------- | ------------------------------------------------------------- |
| `dev`           | 启动 Next.js 本地开发服务                                     |
| `build`         | 生成 OpenNext Worker 构建产物                                 |
| `preview:local` | 使用本地资源启动 Cloudflare Preview                           |
| `preview:prod`  | 使用生产资源启动 Cloudflare Preview                           |
| `deploy`        | 构建并部署到 Cloudflare                                       |
| `cf:local:init` | 初始化本地 D1/本地开发状态（旧 `db:local:init` 迁移为该命令） |
| `cf:types`      | 根据 Wrangler 配置生成类型                                    |

说明：

- `preview:local` 默认使用本地模拟资源；在本地数据库未初始化或需要重建时，先执行 `pnpm cf:local:init`。
- `preview:prod` 使用生产资源进行本地 Preview，不会发布 Worker。
- 远程资源的初始化/改写/删除等操作暂不实现，后续统一纳入 `cf:*` 命令：`TODO(Ben)`。

不建议在 `package.json` 中重复编写复杂的 Wrangler 参数。环境选择、配置文件选择和资源模式统一放在 `scripts/` 中维护。

## 8. D1 数据库管理

### 8.1 Schema 管理（Schema-apply-first）

推荐目录：

```text
db/
├── schema.sql
└── migrations/
    ├── 001_xxx.sql
    └── ...
```

基本原则：

- `schema.sql` 是数据库结构的主要真相源，采用 **Schema-apply-first**。
- 本地初始化、预览和部署前的数据库准备，优先通过执行 `db/schema.sql` 完成。
- `db/migrations/` 可以保留作为历史变更记录或手动运维参考，但不是默认自动执行机制；避免 schema 与 migrations 双轨漂移。
- 不要在生产部署时无条件重建数据库或破坏已有数据。
- 数据库变更应先在本地验证，再应用到生产。

### 8.2 常用操作

本地初始化/重建（通过项目脚本）：

```bash
pnpm cf:local:init
```

本地执行 Schema：

```bash
pnpm exec wrangler d1 execute DB --local --file=db/schema.sql -c wrangler.local.jsonc
```

生产执行 Schema（谨慎操作）：

```bash
pnpm exec wrangler d1 execute DB --remote --file=db/schema.sql -c wrangler.prod.jsonc
```

说明：

- 实际命令应与项目配置文件、数据库绑定名和脚本封装保持一致。
- 远程数据库的初始化/改写/删除等独立运维操作暂不实现，后续统一纳入 `cf:*` 命令：`TODO(Ben)`。

## 9. R2 与 KV

### 9.1 R2

R2 用于图片和文件存储。

本地开发使用 Wrangler 的本地模拟存储，生产环境使用远程 Bucket。

业务代码通过 `IMAGES` Binding 访问，不直接依赖 Bucket 名称。

### 9.2 KV

KV 用于：

- 缓存
- 临时数据
- 低频变化的数据
- 其他适合最终一致性存储的场景

业务代码通过 `CACHE` Binding 访问。

需要注意 KV 的最终一致性，不适合要求强一致性的业务数据。

## 10. 其他 Cloudflare 服务

以下能力按实际需求启用，不要求一开始全部配置。

### Queues

用于异步任务，例如：

- 邮件发送
- 图片处理
- 后台任务
- 非实时通知

启用时需要配置 Queue、Producer Binding 和 Consumer。

### Vectorize

用于向量检索、语义搜索等功能。

启用时需要创建 Index，并配置 `VECTOR_INDEX` Binding。

### Durable Objects

用于有状态任务、协调逻辑和需要持久状态的功能。

需要同时配置：

- Durable Object Class
- Wrangler Binding
- Migration
- Worker 导出

不要仅因为 `worker.ts` 导出了 OpenNext 内部处理类，就认为 Durable Objects 已经完成部署配置。

### Workers AI

用于模型推理等 AI 能力。

通过 `WORKERS_AI` Binding 调用，不需要在业务代码中维护 API Token。

## 11. Secrets 管理

敏感配置通过 Cloudflare Secrets 管理。

例如：

```bash
pnpm exec wrangler secret put AUTH_SECRET
pnpm exec wrangler secret put GITHUB_CLIENT_SECRET
```

查看 Secret：

```bash
pnpm exec wrangler secret list
```

原则：

- 不提交 `.env` 中的敏感值。
- 不将生产 Secret 写入 `wrangler.jsonc`。
- 本地开发可以使用 `.dev.vars`。
- `.dev.vars` 应加入 `.gitignore`。
- 生产 Secret 通过 Wrangler 或 Cloudflare Dashboard 管理。

## 12. TypeScript 类型生成

使用 Wrangler 生成 Cloudflare 环境类型：

```bash
pnpm cf:types
```

生成的类型文件可以用于约束：

- D1Database
- R2Bucket
- KVNamespace
- Ai
- Queue
- DurableObjectNamespace
- Fetcher

优先使用 Wrangler 实际生成的类型，不建议手动重复定义 Cloudflare Binding 接口。

## 13. 部署流程

### 13.1 本地开发

```bash
pnpm dev
```

使用本地 Next.js Dev Server 和本地资源。

### 13.2 本地 Preview

```bash
pnpm cf:local:init   # 首次或需要重建本地 D1 时执行
pnpm preview:local
```

执行：

1. OpenNext Build。
2. 启动 Wrangler Preview Worker。
3. 使用本地模拟资源。
4. 验证 Cloudflare Runtime 兼容性。

### 13.3 生产资源 Preview

```bash
pnpm preview:prod
```

执行：

1. OpenNext Build。
2. 启动本地 Wrangler Preview Worker。
3. 连接远程生产资源。
4. 验证生产环境的 Binding 和运行行为。

此操作不会发布 Worker，但可能访问或修改真实生产数据，Preview 阶段应尽量只读。

### 13.4 正式部署

```bash
pnpm deploy
```

执行：

1. 检查部署配置（优先使用 `wrangler.prod.jsonc`）。
2. 执行 OpenNext Build。
3. 检查必要的生产资源。
4. 按 Schema-apply-first 策略应用 `db/schema.sql`（应保持幂等，避免破坏已有数据）。
5. 部署 Cloudflare Worker。
6. 验证部署结果。

数据库 Schema 变更应当是可审计、可重复执行的步骤；生产环境变更前先在本地验证。远程数据库初始化/改写/删除等独立运维操作暂不实现：`TODO(Ben)`。

## 14. CI/CD

推荐使用 GitHub Actions。

基本流程：

```text
Git Push / Pull Request
          |
          v
    Install Dependencies
          |
          v
      Type Check
          |
          v
        Lint
          |
          v
        Test
          |
          v
       Build
          |
          v
      Deploy
          |
          v
  Cloudflare Workers
```

建议：

- Pull Request：执行检查、测试和构建，不部署生产。
- 主分支合并：执行生产部署。
- 使用 Cloudflare API Token 或支持的 OIDC 部署认证方式。
- GitHub Actions 中的敏感配置使用 Secrets。
- 部署前确保生产 D1 Schema 变更已在本地验证。

CI 中应统一使用 pnpm，清理 npm 相关流程；避免同时维护 npm 和 pnpm 两套锁文件或命令。
