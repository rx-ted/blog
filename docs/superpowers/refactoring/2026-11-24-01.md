# Editor Module Architecture Specification

**Status:** In Progress (Novel path: Phase 1-5 first-pass complete, Phase 6 pending)  
**Last Updated:** 2026-11-25  
**Scope:** NovelEditor / BlockNoteEditor  
**Architecture:** Shared Editor Module + Independent Editor Implementations

## 1. Overview

项目计划同时支持两种富文本编辑器：

- **NovelEditor**：基于 Novel / Tiptap。
- **BlockNoteEditor**：基于 BlockNote。

两种编辑器可能共享部分业务组件和功能，例如文章元数据、自动保存、文件上传、弹窗和编辑器状态展示。

为避免重复实现，同时保持底层编辑器的独立性，采用统一的 `editor` 模块组织代码。

核心设计原则：

1. 共享业务能力，不强制统一底层编辑器 API。
2. Novel 和 BlockNote 保持独立实现。
3. 通用组件不得直接依赖具体编辑器。
4. 通过 Props、Hooks 和 Adapter 连接共享层与编辑器实现。
5. 优先共享稳定、重复出现的功能，避免过度抽象。

### 1.1 Current State

当前代码库与本方案存在差距，重构时应以渐进迁移为前提：

- **现有入口**：`components/NovelEditor.tsx`、`components/NovelEditorClient.tsx`、`components/InlineArticleEditor.tsx`、`components/InlineArticleEditorClient.tsx`。
- **页面接入**：`app/editor/page.tsx` 当前通过 `NovelEditorClient` 渲染编辑器。
- **已有共享雏形**：`components/editor/shared.ts` 已包含部分类型、常量和纯函数，例如 `SaveState`、`EditorViewMode`、`EditorAiTool*`、`AUTOSAVE_DEBOUNCE_MS`、`syncEditorHeadingAnchors`。
- **已有底层工具**：`lib/editor-*` 已承载 Markdown、扩展、AI 编辑、上传、键盘、链接、标题导航等能力。
- **BlockNote 现状**：尚未实现，`package.json` 当前无 BlockNote 依赖。

### 1.2 Target State

- 编辑器相关 UI、hooks、types、adapters 逐步收敛到 `components/editor/`。
- Novel 与 BlockNote 保持独立实现，但复用稳定的共享业务层。
- 旧入口在迁移完成前保留兼容导出，避免路由和调用方一次性改动。

### 1.3 Non-goals

- 不更换 Novel/Tiptap 编辑器引擎。
- 不重写 Markdown 解析、导入导出或现有编辑器扩展行为。
- 不重做文章管理、认证权限、AI 产品能力、主题或搜索。
- 不在结构重构过程中顺手改变产品行为、文案、快捷键或保存策略。
- 不在 BlockNote 未真实接入前，提前设计庞大的通用抽象层。
- 不假设 Novel 与 BlockNote 之间可以通过 Markdown 无损互转所有内容。

## 3. Module Responsibilities

### 3.1 Shared Module

共享模块只处理编辑器共同的业务需求，不处理具体编辑器的底层实现。

| Module             | Responsibility                                           |
| ------------------ | -------------------------------------------------------- |
| EditorHeader       | 标题区域、保存状态、保存和发布操作                       |
| EditorToolbarShell | 通用工具栏布局/容器，不包含具体编辑器命令                |
| EditorStatus       | 保存状态、字数、阅读时间等                               |
| EditorSidebar      | 侧边栏布局                                               |
| EditorMetadata     | 摘要、标签、分类、封面等元数据；标题字段的单一来源需明确 |
| EditorModalShell   | 通用弹窗壳层；业务弹窗按功能归属                         |
| useEditorAutosave  | 自动保存、防抖、重试、请求取消                           |
| useEditorUpload    | 图片、附件、封面上传                                     |
| useEditorMetadata  | 元数据状态和更新                                         |
| useEditorKeyboard  | 通用快捷键；编辑器命令快捷键保持独立                     |
| utils              | 时间、元数据、文档等纯函数                               |

共享模块应尽可能保持与编辑器实例无关。

例如，`useEditorAutosave` 不应该直接调用 Tiptap 或 BlockNote API，而应接收序列化后的文档内容或统一的数据获取接口。

现有 `components/editor/shared.ts` 中已存在的类型和纯函数，应优先作为对齐基线：

- 状态与模式：`SaveFeedback`、`SaveState`、`EditorViewMode`、`PublishStatus`。
- AI 协议类型：`EditorAiToolInsertTarget`、`EditorAiEditArticleContentInput` 等。
- 常量与工具：`AUTOSAVE_DEBOUNCE_MS`、`calcReadTime`、`syncEditorHeadingAnchors`。

新增类型时，应避免与 `lib/article-toc`、现有 AI 工具类型、编辑器存储格式重复定义。

### 3.2 Novel Module

Novel 模块负责 Tiptap / Novel 独有的实现。

| Module           | Responsibility                        |
| ---------------- | ------------------------------------- |
| NovelCanvas      | Novel 编辑器主体                      |
| NovelToolbar     | Novel 专属编辑操作                    |
| NovelSourceView  | Markdown 源码编辑                     |
| NovelPreview     | Novel 内容预览                        |
| useNovelContent  | 内容状态、Markdown 导入导出、模式切换 |
| useNovelToc      | 标题解析、目录和锚点同步              |
| useNovelAiBridge | AI 与 Novel 编辑器交互                |
| useNovelScroll   | 编辑区域滚动和移动端同步              |
| novel.adapter    | 将 Novel API 适配为通用编辑器接口     |

### 3.3 BlockNote Module

BlockNote 模块负责 BlockNote 独有的实现。

| Module               | Responsibility                        |
| -------------------- | ------------------------------------- |
| BlockNoteCanvas      | BlockNote 编辑器主体                  |
| BlockNoteToolbar     | BlockNote 专属编辑操作                |
| BlockNotePreview     | BlockNote 内容预览                    |
| useBlockNoteContent  | Block 文档状态和内容转换              |
| useBlockNoteToc      | 标题解析和目录同步                    |
| useBlockNoteAiBridge | AI 与 BlockNote 编辑器交互            |
| blocknote.adapter    | 将 BlockNote API 适配为通用编辑器接口 |

两种编辑器可以拥有相似的功能，但内部实现不要求完全一致。

## 4. Shared Feature Boundaries

共享与独立的功能划分：

| Feature     | Strategy          | Description                    |
| ----------- | ----------------- | ------------------------------ |
| Header      | Shared            | 共用标题、保存状态和操作区域   |
| Metadata    | Shared            | 共用文章元数据                 |
| Autosave    | Shared            | 共用保存流程和请求管理         |
| Upload      | Shared            | 共用上传 API、进度和文件管理   |
| Modals      | Shared / Optional | 仅共享壳层或确实通用的弹窗     |
| Toolbar     | Partially Shared  | 共用布局，编辑操作独立         |
| TOC         | Partially Shared  | 共用目录数据结构，标题解析独立 |
| AI Bridge   | Partially Shared  | 共用业务协议，编辑器操作独立   |
| Content     | Independent       | 文档模型和编辑操作不同         |
| Preview     | Optional          | 输出格式兼容时可以共享         |
| Source View | Independent       | 根据各编辑器的内容模型实现     |

### 4.1 Capability Mapping

重构时应将现有能力映射到目标模块，避免“架构设计”和“真实功能”脱节：

| 现有能力                      | 当前位置/线索                                                                                 | 建议归属                                  | 备注                                             |
| ----------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| 编辑器入口与页面接入          | `components/NovelEditorClient.tsx`, `app/editor/page.tsx`                                     | 入口层                                    | 迁移期保留兼容路径                               |
| 文章元数据/保存状态           | `components/editor/shared.ts`                                                                 | `shared/types` + `shared/hooks`           | 先对齐现有类型                                   |
| Markdown 导入导出/frontmatter | `lib/editor-markdown.ts`, `lib/import-markdown-post.ts`                                       | 先复用 lib，再评估迁移                    | 不重写解析逻辑                                   |
| 编辑器扩展/节点               | `lib/editor-extensions.tsx`                                                                   | `novel/` 或 `lib/`                        | 属于高风险区域，优先行为不变                     |
| 图片上传/裁剪/封面            | `lib/editor-file-upload.ts`, `components/EditorCoverImagePreview.tsx`                         | `shared/hooks/useEditorUpload` + 相关组件 | 区分通用上传与编辑器专属 UI                      |
| AI 编辑/会话                  | `lib/editor-ai-edit.ts`, `lib/editor-ai-chat-sessions.ts`, `components/EditorAiChatPanel.tsx` | 共享协议 + Novel 专属 bridge/UI           | 复用现有 AI 类型                                 |

| Source/preview/wysiwyg        | `EditorViewMode` 当前三种模式                                                                 | `novel` view state                        | split view 若存在/计划支持，需单独确认并更新类型 |

### 4.2 Avoid Forced Abstraction

不要为了共享而强行统一两个编辑器的内部 API。

例如：

- Novel 基于 Tiptap / ProseMirror。
- BlockNote 使用自己的 Block 文档模型。
- 两者的节点结构、事务、选区、插入和删除操作存在差异。

因此：

- 不共享编辑器实例。
- 不共享底层编辑器命令实现。
- 不要求两种编辑器使用相同的文档数据结构。
- 不在 Shared Module 中直接导入 Novel 或 BlockNote 的 API。

共享层只关心业务结果和通用接口。

## 5. Editor Adapter

为减少业务逻辑对具体编辑器 API 的依赖，可以引入统一的 Adapter 接口。

### 5.1 Interface

```ts
interface EditorHeading {
  id: string
  text: string
  level: number
}

interface EditorAdapter<TDocument> {
  /** 返回编辑器原生文档；仅供编辑器专属逻辑或调试使用。 */
  getDocument(): TDocument

  /** 导出 Markdown，作为 AI/预览/交换的通用格式。 */
  getMarkdown(): string

  /** 导入 Markdown；调用方需意识到可能存在格式损失。 */
  setMarkdown(markdown: string): void

  /** 获取当前选中文本；无选区时返回空字符串。 */
  getSelectedText(): string

  /** 在当前光标或编辑器定义的位置插入内容。 */
  insertContent(content: string): void

  /** 替换当前选区内容。 */
  replaceSelection(content: string): void

  /** 获取标题信息，用于 TOC 或 AI 上下文。 */
  getHeadings(): EditorHeading[]

  /** 可选：编辑器就绪后聚焦。 */
  focus?(): void

  /** 可选：订阅文档变化，用于 autosave/dirty state/字数统计。 */
  subscribe?(listener: () => void): () => void
}
```

该接口是初始设计示例，实际方法应根据两种编辑器的 API 和真实业务需求调整。

Adapter 设计原则：

- 只抽象**已经存在的共享业务场景**，不要为假想需求预留大量方法。
- 方法语义必须明确：输入格式、空选区行为、未就绪行为、失败策略。
- 若某能力只有一个编辑器支持，或支持成本明显高于收益，保持 optional 或留在专属 Hook 中。
- 优先复用现有类型（如 TOC/AI 相关类型），避免适配层再次造型。

### 5.2 Implementations

分别实现对应 Adapter：

```text
novel/
└── adapters/
    └── novel.adapter.ts

blocknote/
└── adapters/
    └── blocknote.adapter.ts
```

两个 Adapter 分别负责：

- 获取当前文档。
- Markdown 导入和导出。
- 获取选中文本。
- 插入和替换内容。
- 获取标题和目录信息。
- 将通用操作转换为具体编辑器 API 调用。

### 5.3 Adapter Usage

共享业务逻辑依赖 Adapter，而不是直接依赖具体编辑器。

例如：

```ts
function useEditorAiBridge<TDocument>(adapter: EditorAdapter<TDocument>) {
  // Read document.
  // Read selected text.
  // Insert or replace content.
  // Get headings.
}
```

实际 React 实现中，需要考虑：

- **引用稳定性**：Adapter 应避免每次 render 生成新对象，必要时用 `useMemo`/`useRef`。
- **初始化时机**：编辑器实例未就绪前，不应调用依赖实例的方法；可通过 `null` adapter、`isReady` 状态或 optional 方法保护。
- **变更通知**：autosave、字数统计等需要订阅机制或明确的 onChange 回调，不要在共享层轮询编辑器内部状态。
- **能力降级**：某操作无法被两种编辑器合理统一时，应保留在各自 Adapter 或专属 Hook 中，不必强行加入公共接口。

## 6. Data Model Strategy

两种编辑器应保留各自的原生文档模型。

例如：

```ts
type NovelDocument = /* Tiptap / ProseMirror JSON */;
type BlockNoteDocument = /* BlockNote document */;
```

业务层可以定义统一的文章元数据：

```ts
interface EditorMetadata {
  title: string
  slug: string
  description: string
  tags: string[]
  category?: string
  cover?: string
}
```

建议区分以下数据：

| Data               | Ownership            |
| ------------------ | -------------------- |
| Article Metadata   | Shared               |
| Novel Document     | Novel                |
| BlockNote Document | BlockNote            |
| Markdown           | Interchange Format   |
| Editor UI State    | Shared / Independent |
| Save State         | Shared               |
| Editor Instance    | Independent          |

### 6.1 Persistence and Interchange

Markdown 可以作为两种编辑器之间的内容交换格式，但不能假设 Markdown 转换能够无损保留所有编辑器特有的节点、属性和交互信息。

在实现前需要明确以下决策（当前文档标记为 TBD）：

| 场景                | 推荐格式              | 说明                                     |
| ------------------- | --------------------- | ---------------------------------------- |
| 编辑器内部编辑态    | Native document       | 保留编辑器原生能力和节点信息             |
| 自动保存/草稿持久化 | TBD                   | 需确认现有存储格式与兼容策略             |
| 发布内容存储        | TBD                   | 需确认数据库/内容管道的 canonical format |
| AI 输入/导出/预览   | Markdown              | 允许有损，但需在产品层明确预期           |
| 编辑器切换迁移      | Markdown 或显式转换器 | 必须提示可能的格式损失                   |

如果需要完整保留文档格式，应保存对应编辑器的原生文档数据。任何跨编辑器迁移都应有明确的兼容策略和降级提示。

## 7. Component Communication

推荐使用 Props 和 Adapter 进行组件通信。

原则：

1. 共享组件不直接获取编辑器实例。
2. 编辑器入口负责初始化编辑器和组装依赖。
3. 专属 Hook 负责编辑器内部状态和操作。
4. 共享 Hook 通过通用数据或接口与编辑器交互。
5. 不要过早引入全局 Context。

如果多个深层嵌套组件确实需要共享大量状态，再考虑引入 `EditorProvider`。

避免创建一个包含所有状态、回调、编辑器实例和业务逻辑的巨大 Context。

补充约束：

- 标题、元数据、保存状态应有单一来源，避免 Header、Metadata、Autosave 各自维护副本。
- 通用快捷键与编辑器命令快捷键分离：前者可共享，后者属于 Novel/BlockNote 实现。
- 业务弹窗不要全部堆入 `EditorModals`；只有真正通用的壳层或跨编辑器复用弹窗才进入 shared。

## 8. Refactoring Strategy

将现有较大的 `NovelEditor.tsx` 按照职责逐步拆分。

建议顺序：

### Phase 0: Baseline and Guardrails

在移动代码前先建立基线：

- 盘点现有入口、调用方和关键行为：导入 Markdown、frontmatter、图片上传、autosave、发布、AI 编辑、TOC、快捷键、移动端布局。
- 为纯逻辑补 characterization tests：metadata、markdown/frontmatter、TOC、autosave 状态机、时间/字数计算。
- 明确 `lib/editor-*` 与 `components/editor/*` 的边界，避免迁移过程中出现双份实现。
- 保留旧 import 路径的兼容导出策略。
- BlockNote 若未立项实现，只做设计预留，不提前引入依赖和空壳抽象。

### Phase 1: Extract Types and Utilities

优先抽取：

- 编辑器相关类型。
- 元数据类型。
- 时间和阅读时间计算。
- 标题解析与文档处理。
- 纯函数和常量。

优先复用 `components/editor/shared.ts` 和现有 `lib/editor-*`，避免重复造轮子。

### Phase 2: Extract Shared Business Logic

抽取：

- `useEditorAutosave`
- `useEditorUpload`
- `useEditorMetadata`

确保抽取后行为保持一致。autosave 需要特别关注现有 debounce、重试、请求取消和 dirty state 语义。

### Phase 3: Extract Novel-specific Hooks

抽取：

- `useNovelContent`
- `useNovelToc`
- `useNovelAiBridge`

## 9. Design Constraints

以下约束应作为后续开发规范：

- [ ] NovelEditor 和 BlockNoteEditor 必须保持独立。
- [ ] 两个编辑器统一归属于 `components/editor/`。
- [ ] 共享组件和 Hook 放在 `shared/`。
- [ ] 编辑器专属实现放在各自目录。
- [ ] Shared Module 不得直接依赖 Novel 或 BlockNote。
- [ ] 不共享具体编辑器实例。
- [ ] 不强制统一底层文档结构。
- [ ] 共享业务逻辑优先依赖通用接口。
- [ ] Adapter 只抽象实际存在的共同能力。
- [ ] 迁移期间保留旧入口兼容导出，直到调用方完成迁移。
- [ ] `lib/editor-*` 与 `components/editor/*` 职责边界明确，禁止长期重复实现。
- [ ] 保持现有业务行为，避免拆分过程中引入功能回归。
- [ ] 重构前后关键路径有验证：导入、保存、发布、AI、TOC、上传、快捷键。
- [ ] 不为了文件数量而过度拆分组件和 Hook。

## 10. Final Architecture

最终采用三层组织方式：

```text
Editor Module
│
├── Editor Entry
│   ├── NovelEditor
│   └── BlockNoteEditor
│
├── Shared
│   ├── Components
│   ├── Hooks
│   ├── Types
│   └── Utils
│
└── Implementations
    ├── Novel
    │   ├── Components
    │   ├── Hooks
    │   ├── Adapters
    │   └── Types
    │
    └── BlockNote
        ├── Components
        ├── Hooks
        ├── Adapters
        └── Types
```

**最终原则：共享业务能力，独立编辑器实现，通过 Adapter 连接两者。**

该架构允许后续增加新的编辑器实现，同时避免共享层与特定编辑器产生强耦合。
